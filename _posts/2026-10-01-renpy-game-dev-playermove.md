## 1. 들어가며

Ren'Py는 비주얼 노벨 제작에 많이 사용되지만, 화면과 이미지의 위치를 직접 제어하면 간단한 2D 게임도 구현할 수 있다.
이번에는 Ren'Py에서 Top-down 방식의 게임 플레이어 이동을 구현해 보았다.
처음에는 Ren'Py에서 제공하는 viewport를 활용하는 방식으로 접근했지만, 이후 충돌 검사와 같은 기능을 추가하려고 하면서 구조적인 한계에 부딪혔다.
결국 카메라 좌표와 맵 좌표를 분리하고, 키 입력 역시 단순한 이벤트가 아닌 현재 입력 상태로 관리하는 방식으로 구조를 변경했다.

## 2. 구현하려는 것

- Top-down 방식의 맵

- 플레이어가 맵 위를 자유롭게 이동

- 플레이어는 화면 중앙에 고정

- 플레이어가 이동하는 것처럼 보이지만 실제로는 맵이 반대로 이동

- 화살표키를 이용한 이동

- 이후 벽 등의 충돌 검사 추가 가능

- 맵 영역 밖으로 이동하지 못하도록 제한할 수 있는 구조

## 3. 첫 번째 시도 - viewport

### 3-1. 왜 **viewport**를 사용했는가?

Ren'Py에는 화면의 특정 영역을 스크롤할 수 있는 viewport라는 기능 존재한다.
따라서 처음에는 굳이 별도의 카메라 시스템을 만들 필요 없이, **‘기존의 Ren'py 기능인 viewport를 플레이어가 바라보는 영역으로 사용하면 되지 않을까?’**라는 생각으로 접근했다.

그렇게 실제로 구현한 코드는 다음과 같다.

```
default camera_x = ui.adjustment()
default camera_y = ui.adjustment()

transform map_zoom:
    zoom 5.0

screen viewport_example():
    button:
        action [Show("main_screen"), Return()]

        viewport id "vp":
            xysize (X_FULL, Y_FULL)
            draggable False
            arrowkeys True

            xadjustment camera_x
            yadjustment camera_y

            add "assets/images/washington.jpg" at map_zoom
```

이때 **arrowkeys**를 **True**로 하여서 화살표키를 누르면 이동할 수 있게 하였다.

### 3-2. **viewport**를 이용했을때 생기는 문제들

그러나 위 방식을 이용하면 두가지의 문제가 생기게 된다.

**첫번째로, 화살표키를 꾹 눌렀을때 계속해서 이동을 하지 않고 한번 이동하고 멈춘다는 것이다.**
그렇기에 화살표를 꾹 눌러서 이동하게 하려면 viewport의 arrowkeys가 아닌 직접 키 이벤트를 만들어야한다. 그러나 그런 방식을 이용하면 굳이 viewport를 고른 이유가 없어진다. 화면이 이동하는 기능을 직접적으로 구현하지 않기 위해 viewport를 사용했는데 정작 viewport의 기능을 쓰지 못하는 상황이기 때문이다.

**두번째 문제는 현재 좌표의 상태를 알기 힘들다는 점이다.**
앞선 문제로 **viewport**의 **arrowskeys**를 쓰는 대신 직접 구현한다고 생가해보자. 그렇다면 현재 플레이어의 위치가 맵 위에서 어느 지점에 있는지 정확한 좌표를 알아야한하다. 그러나 **viewport**에선 그 좌표를 확인할 방법이 없다. 아니, 정확히 말하면 맵의 기준에서 플레이어가 어디에 위치해 있는지 알 수 없다.

이게 무슨 말이냐면, **viewport**의 기준에서는 플레이어의 위치를 얻을 수 있다. 그러나 그 좌표는 현재 화면(viewport) 안에서 플레이어가 어디에 있는지를 나타내는 좌표일 뿐이다.

예를 들어 **viewport**의 크기가 **1280x720**이고 플레이어가 화면 중앙에 고정되어 있다면, 플레이어의 위치는 항상 (640, 360)과 같이 동일하게 나타날 것이다. 실제로 플레이어가 맵의 왼쪽 위에 있든, 오른쪽 아래에 있든 **viewport** 입장에서는 플레이어가 화면의 중앙에 있기 때문에 좌표가 변하지 않는다.

반대로 내가 필요한 것은 맵을 기준으로 플레이어가 어디에 위치해 있는지를 나타내는 좌표이다. 맵의 (100, 200)에 있다가 오른쪽으로 이동했다면 (150, 200)과 같이 플레이어의 월드 좌표가 변화해야 한다.

즉, **viewport**가 제공하는 좌표는 다음과 같은 개념이다.

```
Viewport 기준 좌표
→ "현재 화면에서 플레이어가 어디에 있는가?"
```

내가 실제로 필요로 하는 좌표는 다음과 같다.

```
Viewport 기준 좌표
→ "현재 화면에서 플레이어가 어디에 있는가?"
```

문제는 **viewport**자체는 화면을 이동시키는 기능에 초점이 맞춰져 있기 때문에, 내가 원하는 형태의 플레이어 월드 좌표를 직접 관리하기에는 적합하지 않다는 것이다. 따라서 **viewport**의 스크롤 기능을 카메라 시스템 자체로 사용하는 것보다는, 플레이어의 위치와 카메라의 위치를 직접 관리하고 그 결과를 화면에 반영하는 방식이 더 적합하다고 생각하였다.

## 4. 두 번째 시도 — 좌표계 분리

앞선 문제를 해결하기 위해 좌표를 하나로 관리하지 않고 두 개의 관점으로 나누어보았다.

실제로 화면에 보이는 스크린의 크기를 기준으로하는 camera좌표계, 그리고 실제 화면에 표시되는데 사용되진 않지만 내부적으로 여러 요소들의 좌표계산에 이용될 map좌표계이다.

말로 설명하면 어려우니 그림을 참고하면 보다 쉽게 이해할 수 있으리라 생각한다.

= 그림제시

다음 그림을 보면 두개의 층으로 나뉜 레이어를 볼 수 있다. 각 레이어는 Camera와 Map의 크기라고 생각하면 된다.

```
Camera 좌표계의 크기 = 스크린(실제 게임화면)의 크기기
Map 좌표계의 크기 = 맵 이미지의 크
```

이때 중요한 점은, 대부분의 좌표 계산이 Map좌표계를 기준으로 이루어진다는 점이다.

Camera의 좌표계에서 플레이어의 위치는 camera의 (width/2, height/2)로 고정되어있는 반면, Map의 좌표계에서 플레이어의 위치는 변할 수 있다. 이를 통해서 우리는 플레이어의 정확한 좌표를 계산할 수 있게된다. 다른말로, 맵 위에서 플레이어가 현재 어디에 위치하는지 알 수 있다는 것이다.

이렇게 되면 나중에 장애물과의 충돌을 구현하기도 쉬워진다. 맵 좌표를 기준으로 장애물의 좌표와 플레이어의 좌표를 둘다 가지고 있으니 말이다.

또한 키 이벤트를 구현할 수 있다. 이전 방법으로는 좌표 계산이 불가능했어서 이벤트를 만들지 못했지만, 좌표 상태를 알 수 있는 지금은 가능하다.

키 이벤트로 플레이어의 움직임을 구현하는 방법에 대해서는 다음 글에서 자세히 설명하겠다.

여기까지 읽는라 수고 많았고, 누군가에게는 도움이 되었으면 하는 바람이다.
